# M9 基线与独立验收器设计

用户要求实施阶段目标中的 M9。沿用 Python 标准库、Git 和 M6 Docker 执行器；本步交付修改前基线、受保护的五项 Todo 检查、失败分类和与候选文件内容绑定的机器结果。M10 的 Diff/综合报告仍待实施。

## 职责与数据流

`acceptance/snapshot.py` 从固定提交读取原始 blob，遍历活动工作区的常规文件（包括未跟踪和忽略文件），拒绝链接、硬链接、特殊文件和资源超限。只有 `todo_app/` 可变化，其他文件必须与固定提交逐字节相同。路径和文件字节共同计算 SHA256；Git HEAD 一并记录。快照只含已检查字节，容器不读取实时工作区。

`acceptance/checks.py` 复用 M6 的权限、资源、网络及清理策略，在快照上执行固定 pytest 命令。固定规则同时覆盖一项 404 验收和四项正常行为回归；禁用候选 conftest、自动插件和配置发现。容器在退出前通过唯一 Base64 标记输出 JUnit XML，宿主有界扫描日志并保存 XML，不新增宿主可写挂载。JUnit XML 只接受精确五项名称、模块身份、统计与真实退出码，缺失、重复、跳过、错误或不一致的退出码都不能证明通过。

`acceptance/service.py` 在基线提交且文件完全未改的活动工作区上记录基线。`verify` 仅使用同工作区已保存的有效基线和其完整镜像 ID，区分 passed、existing_failure、new_failure、environment_error、rejected、stale。原失败仍存在不能标为 passed；新增失败按测试身份与基线比较。候选运行前后重新检查实际工作区摘要，变化则结果失效。基线/候选执行错误保留诊断，不将失败基线当成有效前置条件，失败的基线重试也不覆盖先前有效引用。

`acceptance/cli.py` 提供 baseline/verify/show；CLI 与 Agent 工具都不能提交命令、测试名单、镜像或权限覆盖。宿主侧 JSON 保存于工作区根的 `.acceptance/`，完整容器日志及 XML 在 `.runs/`，都位于候选和来源仓库之外。报告包含规则摘要、候选 HEAD/内容摘要、环境、运行记录与日志路径，`show` 重新检查候选以揭示陈旧结果。

## 范围与局限

当前仅支持固定 Todo 示例、单主机且可信仓库。文件和摘要检查不构成对抗恶意 Python 测试结果伪造或并发目录替换的完整安全证明；快照提供实际被测字节的稳定性，运行前后检查检测可观察到的工作区变化。持久化状态是本地验收证据，不代替未来 Job 数据库。M9 不实现模型、通用命令、API、Worker 或 M10 综合产物。

## 验收

先验证缺失功能红灯，再验证：干净基线要求、无基线拒绝、规则保护、未跟踪/忽略文件摘要、删除/新建/路径边界和链接保护、测试身份与退出码一致性、原有/新增失败、环境故障、同镜像和候选失效、跨进程查询。真实 Docker 流程先得到四通过一失败，再应用预设补丁得到五通过；故意引入回归得到 new_failure，改权威测试得到 rejected；最后恢复演示文件并经 M5 清理，来源保持不变。
