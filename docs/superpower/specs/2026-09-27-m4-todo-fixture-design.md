# M4 固定 Todo 示例仓库设计

## 目的与边界

M4 为 AgentForge 后续的代码修改与验收练习提供一个可重建的目标仓库。它不是 AgentForge 的服务端，也不承担真实用户数据。完成后，开发者能从受版本控制的模板生成独立的本地 Git 仓库，记录其基线提交，并在该提交上稳定看到同一个预期失败。

本步只建设示例仓库，不创建 M5 工作区、不运行 Agent、不引入数据库、容器或网络数据。AgentForge 现有 M1–M3 代码保持原状。

## 仓库边界与文件职责

- `examples/todo_fixture/` 是 AgentForge 跟踪的完整示例源码模板，不含嵌套 `.git`。它是基线内容的唯一可分发来源。
- 模板包含 FastAPI 应用、pytest 用例、直接依赖声明和锁定全部传递依赖的文件；`.gitattributes` 统一文本行尾，避免跨机器复制改变 Git 树。
- 模板作为独立小项目，提供 `README.md`、`项目最终架构.md`、`阶段步骤实现.md`。这些文档说明其教学目的、当前能力、故意缺陷、启动与验证方法；修复缺陷属于后续阶段，不写成已完成。
- `scripts/create_todo_baseline.py` 只把模板复制到项目内被忽略的 `.local/todo_baseline/`，初始化独立 Git 仓库并创建固定元数据的初始提交。目标已存在时拒绝覆盖，不修改 AgentForge 的 Git 索引或提交。
- AgentForge 根目录记录基线提交 ID 和复现命令，供 M5 使用；`.gitignore` 忽略 `.local/`。基线 ID 不写进模板本身，避免提交内容与 ID 循环依赖。

## 示例 API 与故意缺陷

使用 Python 3.11+、FastAPI、Pydantic、pytest、httpx2、Uvicorn。应用在内存中保存 Todo；每次调用 `create_app()` 得到独立状态，不使用数据库或外部接口。[Starlette 测试客户端文档](https://www.starlette.io/testclient/)目前建议使用 httpx2，避免旧 httpx 路径的弃用警告。

- `POST /todos` 接受 `{"title": "学习 AgentForge"}`，返回 201、递增整数 `id`、原样 `title` 和 `completed: false`。
- `GET /todos/{todo_id}` 对已存在 ID 返回 200 和对应 Todo。
- 对不存在的正整数 ID，期望行为是 404；**基线故意返回 200**。这是唯一预置缺陷，留给后续修复练习。

模板测试至少分别覆盖创建、查询已存在项、查询不存在项。基线上前两类通过，缺陷测试因实际状态码 200 与期望 404 不符而失败；不得通过跳过、xfail 或改写断言来掩盖失败。

## 依赖与生成流程

模板声明少量直接依赖，使用可读的锁定文件固定全部依赖版本。锁定文件在 M4 实现时用本机可用的 `uv pip compile --universal` 生成；日常安装可用 `python -m pip install -r ...`，不要求使用者安装 uv。生成基线前在独立虚拟环境安装并验证，不污染 AgentForge 的 `.venv`。

生成器不下载依赖、不运行 Todo 代码。它复制模板、执行本地 Git 初始化与提交，打印完整提交 ID。只从固定模板产生基线，Git 作者、提交者、时间和提交消息固定；目标已存在时报告清楚的错误，不删除或覆盖现有目录。根目录记录一次实际生成和验证得到的提交 ID；若其他环境产生不同 ID，应检查文件内容与 Git 设置，而不能默默把不同提交当成已验证基线。

## 验证与交付

1. AgentForge 原有单元测试和 Ruff 检查仍通过。
2. 生成器的测试证明：新目录可形成独立 Git 仓库；重复生成不会覆盖它；模板目录本身没有嵌套 Git 仓库。
3. 在生成仓库中安装锁定依赖并运行 pytest：创建和正常查询通过，缺陷测试稳定失败，失败原因明确是缺失 Todo 的 HTTP 状态码。
4. 读取生成仓库的 `HEAD`，确认与根目录记录一致；生成仓库与 AgentForge 父仓库分别显示各自的 Git 顶层目录。

M4 的“成功”指成功交付**可复现的红色基线**，不是让示例仓库全部测试通过。后续 M5 只能以记录的基线提交创建工作区，不能直接修改模板或原始生成仓库。
